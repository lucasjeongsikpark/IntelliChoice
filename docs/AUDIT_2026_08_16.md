## 1. The finding behind the findings

**All four sweeps independently reported the same structure: the two apps have been fixed in
alternating directions, and nobody tracked the symmetry.**

D-347 recorded one direction — *"learning-web solved four of these and chat-web never received
the fix"* — and named the cause: two independently deployed frontends with a no-shared-code
posture will silently diverge. **The reverse is now equally true and is recorded nowhere**, and it
extends to the backends, which D-347 never covered:

| fix | shipped in | never ported to | consequence found |
|---|---|---|---|
| request deadline + cancel (D-352) | chat-web | learning-web | a hung fetch freezes an exam permanently (P1) |
| 401 → clear token + re-auth (D-347) | chat-web | learning-web | mid-session expiry is unrecoverable (P1) |
| focus trap + `inert` (D-350) | chat-web | learning-web | Tab out of a modal onto the exam behind it (P2) |
| accessible name on the composer (D-350) | chat-web | learning-web | tutor chat input is unlabelled (P2) |
| turn deadline (D-346) | chat-api | learning-api | two paths outlive CloudFront's 60 s (P2) |
| advisory lock per thread (D-346) | chat-api | learning-api | one graph thread can be invoked twice (P2) |
| re-read before publish (D-358 + D-369) | narrative scheduler | hint scheduler | **D-356's symptom, unfixed, in the second publisher (P1)** |

**Seven fixes, one direction.** The last row is the most serious finding in this audit and is the
clearest instance of the pattern: D-356 was treated as a launch blocker, fixed twice over two
sessions, and the same defect sat untouched in the sibling publisher the whole time.

The practical consequence for the fix pass: **most of the P1/P2 work is porting code that was
already written, reviewed and tested once**, not designing anything new.

## 2. P1 — a launch journey is broken

### P1-1 · The hint personalizer erases the help a student chose · `hint_personalization_scheduler.py:174-196`
D-369's defect exactly, in the publisher that never got D-358's signal or D-369's re-read.

The interleaving: the student answers wrong, clicks "Get a hint", and the scheduler starts a
~2.3 s Bedrock call. Inside that window the student clicks "Watch a video". `intervention_choice`
commits the video — but it **does not advance `last_study_attempt_id`**, which is the only field
this scheduler's guard checks, so the guard passes. The task then builds a frame from its stale
read and publishes; every SSE frame replaces the whole snapshot, so hint 1's text replaces the
video.

**Not recoverable.** The pause is closed, nothing republishes, and `stream._initial_snapshot`
gates `intervention` on `hint_ladder_awaiting_choice` — false at every terminal rung — so a
refresh shows no help at all. The student spent their one intervention on nothing.

Existing tests cover only "the student moved to a *different attempt*". Fix: port
`_help_is_on_screen` + the publish-time re-read from `stage_narrative_scheduler.py`.

### P1-2 · No request has a deadline, and the busy latch turns one hung fetch into a dead exam · `learning-web/src/api/client.ts:32`
No `AbortController`, no `signal`, no timeout anywhere in `learning-web/src` (verified by grep).
`useLearningSession`'s `busyRef` is set before the call and cleared in a `finally` that never
runs if the fetch never settles.

A student presses Submit on question 6; the connection stalls (mobile handover, captive portal, a
half-open connection of the kind D-364 documented). Every option, Submit, Skip, Flag and the nav
bar stay disabled forever. The server-side timer keeps running, and `submitBlocked` then refuses
"Submit exam" because items are unanswered — **the student can neither answer nor submit.** D-241
records that this state must never exist. Only a reload escapes, and nothing on screen suggests it.

chat-web fixed this in D-352 with a 55 s client timeout above the server's 50 s deadline.
learning-web is worse off than chat-web ever was, because chat-web had no latch serialising the
whole UI behind one request.

### P1-3 · A 401 instructs the student to do something no screen offers · `learning-web/src/api/errors.ts:74`
The message is *"You've been signed out. Sign in again to keep going."* Nothing acts on the 401 —
one grep hit, the rule itself. The only code clearing the token is `handleLogout`, reachable only
from `StartScreen`, which renders only when there is no session.

**Token TTL is one hour; a session is 25–40 questions** (pre-exam, five study skill lines,
post-exam) plus hint ladders and tutor turns. Passing an hour is the normal path, not an edge
case. On expiry every answer fails, the SSE stream dies with the same dead token, and the
Reconnect button re-opens with it and fails again, forever. A reload does not help — the dead
token is still in `localStorage`, so the login screen never renders. Recovery means a new tab,
which abandons the session.

chat-web's D-347 `handleSignedOut` is the fix, wired as `useChatSession`'s third argument;
`useLearningSession` has no such parameter.

### P1-4 · A mid-turn reload manufactures a refusal that never happened · `chat-web/ChatScreen.tsx:178`
`resolve_role` clears `answer`/`citations` at turn start while `client_turn_id` is already in the
checkpoint, and `/stream` emits its initial snapshot on every connect with no "is a turn running?"
guard. D-348's matcher finds the id, matches confidently, and commits the empty response.

The visitor reloads two seconds into a 6–11 s question and reads *"No answer came back for that
one. Try asking it again."* They follow it and get a 409; seconds later the real answer overwrites
the refusal. In a product where a refusal is a first-class outcome, this fabricates one and
instructs an action that fails.

**`sse-reconnect.spec.ts` names this case and stubs a completed-answer frame** — the one variant
the real server cannot emit for a turn still in flight.

### P1-5 · The crash sink has no metric and no alarm · `client_errors.py` (both apps)
Built for learning in D-328 and for chat today in D-372, precisely so *"a student's blank screen"*
reaches someone. `$.event = "client_error"` is directly metric-filterable. There is no filter, no
alarm, no counter. **The reporting half shipped; the noticing half did not.** A frontend deploy
that white-screens one browser family sits until a human complains.

Highest value per line in the audit — both ends already exist.

### P1-6 · Four nightly jobs report in unstructured `print()` · `terraform/modules/observability/pipeline.tf`
Read live from staging: all four enabled schedules fired today and emitted plain text. A
three-day structured-event query over the ops-task log group returns only the deploy-time loader.

Today's memory-consolidate line: **0 facts added, 3,181 events dropped over the call cap, 14.11
cents spent** — a job succeeding at doing nothing. "Has the 90-day chat purge deleted anything
this month, or has it been exiting 0 against a broken cutoff?" cannot be answered from metrics;
it requires opening log streams and reading prose. `pipeline.tf` makes exactly this argument and
fixed it for the generation pipeline only.

### P1-7 · No dead-man's switch on any schedule · `terraform/modules/scheduled-jobs/main.tf:235`
The alarm watches ECS task exit ≠ 0 — a job that runs and fails. A job that **never runs** emits
no task-state event, so no rule matches and no alarm fires. Zero `AWS/Scheduler` alarms exist.
The only instrument is a manual `make scheduler-evidence`.

For a 90-day retention promise over minors' chat data, the absence of a failure is
indistinguishable from the absence of a run, and silence is the dangerous direction. Fix: an alarm
per job with `treat_missing_data = "breaching"` — the inverse posture of every existing alarm,
because here missing data *is* the incident.

### P1-8 · A broken attendance gate goes silent instead of spiking · `learning-api/graph/nodes.py:379`
The `except` returns **above** the `ATTENDANCE_CHECKS.inc()`. And the metric declares
`"present" | "blocked" | "unknown"` while `"unknown"` is emitted nowhere in the repo — the slot
was designed and never wired.

This matters because D-152 §2 records that `signups.attended = null` → UNKNOWN → blocked is a
**routine** production path. So the one metric that would separate "the MySQL adapter is down"
from "quiet night" reads flat in both cases, and the ALB stays 200 throughout because a blocked
start is a successful response. Two lines to fix.

### P1-9 · D-329's detection gap is unchanged · `metrics.py`, `terraform/`
The incident — 117 `background_hint_personalization_failed` in 48 hours, the only ERROR the
service emitted, invisible because a failed personalization is deliberately indistinguishable from
the canonical hint — is fixed. **The gap that let it run for 48 hours is not.**

learning-api has no degradation counter of any kind. Three detached schedulers, six fallback paths
in `tutor.py` (including the answer-leak and monotonicity safety trips, which are content-safety
events), and four paths that return `None` on failure with no log at all. `grep -rin "background_"
terraform/` returns **0**. One metric filter over `{ $.event = "background_*_failed" }` covers all
of them.

### P1-10 · 22 product KPIs bridged to CloudWatch, zero alarms on any of them
Verified live: 21 metrics in each service namespace, 26 alarms, **not one referencing a product
KPI.** `alarms.tf` opens by criticising exactly this pattern for an earlier set of metrics.

Sharper instance: `qa_service_degraded_total` is **absent from the namespace entirely** —
`prometheus_client` emits no series until `.labels()` is first called, so the counter built so a
Bedrock outage stops reading as a surge of off-topic questions cannot be alarmed on until after
the first outage creates it. Fix: pre-initialise the labels at import, then two or three
low-watermark alarms (`learning_sessions_completed_total`, `qa_answers_total`).

## 3. P2 — real damage with a workaround

**Timing.** learning-api has no turn deadline, so `POST /exam/finalize` (via the inline
`post_outro` narrative) and the tutor chat can reach 61.5 s against CloudFront's 60 s — measured
at 65–81 s by D-208, which moved consolidation off the path and left `post_outro` on it. The
student gets an opaque edge 504 while the server finishes correctly a second later; on `/stream` a
non-2xx is terminal for `EventSource`, so that tab receives no live push for the rest of its life.
· learning-api has **no advisory lock**, so two tabs on one session (Chrome's Duplicate Tab copies
`sessionStorage`) can invoke one LangGraph thread concurrently; two `ExamTimer`s expiring on the
same second is the cleanest trigger. · The SSE relay fires NOTIFY as an unreferenced task onto one
shared asyncpg connection — a second concurrent publish raises *"another operation is in
progress"*, which is swallowed, silently dropping the cross-replica event (D-334's bug returning,
and the log line carries no session id). · A **failed** answer still locks the question read-only
with no rollback, so the item is graded incorrect at finalize and the pre-exam score, the learning
gain, and the parent report are all silently wrong by one item.

**chat-web.** Retrying a failed escalation drops the `escalate` flag, so it re-enters the scope
guard as an ordinary question, gets refused, and offers the same button again — a loop that never
reaches a human. · The client re-derives the refusal reason and contradicts the server on
`sources_conflict`; `reason` is on the wire, typed as *"the field to branch on"*, and read by no
component. · A question over 2,000 characters gets a 422 with no 422 rule, so the message never
mentions length and retry re-sends identical text forever. · "Stop" aborts only the HTTP request;
the graph runs on under its 50 s deadline holding the session lock, so the next question is
refused as *"still working on your last question."* · **The approval modal — the one screen that
sends real email — has no `max-height` and no `overflow` while the body is locked**, so a long
body puts the heading above the fold and both buttons below it, with no visible close. · The
composer loses focus on every send and nothing restores it.

**learning-web.** Neither modal traps focus: two Tabs from "Submit exam?" reach the exam options
behind the scrim, where a keypress answers a question the student cannot see, and `aria-modal`
means a screen reader announces nothing. · **30 of 33 topics render their raw internal id** on the
dashboard (`g4_multiplication_division`); the student picks "Word Problems" and reads
`g3_word_problems` back in their own history. · The exam timer's `aria-live="assertive"` updates
every second for the final minute — sixty interruptions while trying to read a question. · The
tutor chat flattens 429, 401 and 503 into one transient message and clears the input before the
await, so a failed send costs the student their typing. · `ChildSelectionScreen` has no error
surface and no exit. · "Back to start" on the results screen redraws the results screen.

**Observability.** An unhandled non-Bedrock exception bypasses both middlewares, producing no JSON
access line, no `trace_id` and no `http_requests_total{status="500"}` — only the ALB knows. ·
Bedrock spend is attributable per day and per app but **never per student or per session**, so
when the spend-spike alarm fires, "which student is looping?" is not answerable. · SSE has no
telemetry at all: no connection gauge, no disconnect counter, no delivery counter. · Fifteen log
sites interpolate values into the message, which breaks `$.event` filters *and* routes free text
past the key-based PII filter. · All 26 alarms deliver to one email address, so at 2am the alarm
and the parent's email arrive together at 8am.

**Inverse risk, worth its own line** *(✅ resolved 2026-08-17, D-394 — redacted in
`JsonLogFormatter`, which is the "one place" this paragraph correctly identified)*: `exc_info`
tracebacks and the gateway's `detail` are free
text the key-based denylist cannot inspect. A Pydantic `ValidationError` embeds the offending
input, and on a structured-output repair failure that input is model output derived from a
student's question. A hazard, not a confirmed leak — the criterion-9 scan found logs clean over
3,269 events. `redact_free_text` already exists and one place covers every call site.

## 4. P3

Cross-app metric pollution (both apps export each other's counters at zero).

## 5. Suggested fix order

The batching matters more than the ranking — three batches cover most of the list.

**Batch A — port the seven fixes that already exist.** Section 1's table. This is the largest
share of P1/P2 and the lowest risk, because each fix was written, reviewed and tested in the
sibling app. Start with P1-1 (the hint scheduler), because it is the only one where the unported
fix leaves a *launch journey* broken.

**Batch B — point CloudWatch at logs that are already correct.** P1-5, P1-6, P1-7, P1-9 close with
a handful of `aws_cloudwatch_log_metric_filter` resources plus alarms, over events that already
exist and are already well named. P1-8 is two lines of Python. No new infrastructure.

**Batch C — the client-state defects that corrupt a number.** The failed-answer lock (a wrong
parent report), and chat's two retry loops that can never succeed.

Everything else is independent and can be taken in any order.

## 6. What this audit says about the process

Three of today's findings, and three found earlier in the same session, are the same shape:
**a check that is correct and no longer checks.** A spec that names a case and stubs the one
variant that passes. A metric whose label was designed and never emitted. A decision accepted as
"cosmetic and rare" whose premise expired when the bank grew from 3 topics to 33. A guard asking
the right question a moment too early.

The recurring cause is that each fix ended at the log line, the assertion, or the entry — and not
at the thing that would notice when it stopped being true. That is worth a habit rather than
another finding: when closing an item, ask what would fail if this regressed tomorrow, and if the
answer is "someone would have to look", the fix is not finished.
